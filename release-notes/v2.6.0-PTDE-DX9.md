# Dark Souls: Prepare to Die Edition, FPS Unlock v2.6.0

Smoother and faster, with the same picture. Files: `xinput1_3.dll`, `PTDE-FPS-Unlock.ini` and `dxvk_d3d9.dll`, next to `DARKSOULS.exe`. Current Steam build only (`SizeOfImage` `0x11C2000`). Remastered is unchanged (v2.5.0).

Everything new is on by default, and every part has an INI switch.

## Smoother: the game's mutexes without kernel calls

- **`FastMutexes`** (new). The game's mutexes (`DLPlainMutex`) are Windows kernel mutexes: every time one is taken and every time it is given back is a call into the Windows kernel, about 1.7 microseconds a pair, and the game thread takes them about 200 times a frame (its sound and map updates among others). A kernel mutex also hands itself to the thread that waited for it first, so the game thread kept queuing behind threads that still had to be woken: in a heavy Blighttown view one frame in twenty took 7.5 to 10 ms where the others took 2.6. They are now taken and given back with one interlocked instruction (about 5 nanoseconds), under the same rules: the thread holding one can take it again, an unlock by another thread fails as before, a thread that has to wait sleeps. In that view at 4K the 95th percentile of the frame times went from 7.6 to 3.3 ms and the slowest frame from 10 to 3.5 ms, at the same average; at 1280x720, where the game thread is the limit, from 351 to 495 FPS. The game's sound update alone went from 0.94 to 0.14 ms a frame there. Where the game's x86 code runs translated for another CPU (Android with GameNative or Winlator, Windows on ARM) it stays off unless `FastMutexes = always`, as `FastReadLocks`.
- **`CacheInputReads`** now applies on Windows too (`auto`, the default). The game read the keyboard and mouse four times a frame; reading once and sharing the reading is about 2% more frames where the game thread is the limit (it was on only under Wine before).

## Faster where the render thread is the limit

In views full of effects (the Demon Ruins, Quelaag's Domain) the render thread limits the frame rate. About 9% more frames in the Demon Ruins at 4K (280 to 305 FPS on a Ryzen 7 5800X3D), each step checked against the game's own code or with screenshots of a frozen frame:

- **Filter states with `AnisotropicFiltering`**: the min filter, mip filter and anisotropy level that the anisotropic filtering upgrades were never answered as repeats; now they are, when nothing would change (+3%).
- **The effects' keyframe curves** with one lane in registers, like the four-lane ones (`RenderMathPrecision = relaxed`, render thread only; +1.9%).
- **The effects' four busiest forwarding helpers** done directly, bit for bit as before (+1.7%).
- **The bones' matrices** set with whole-row moves (+2%).
- **This mod's own shader lookups** without locks (+1.5%).

## DSfix

- **`HighPrecisionColor` beside DSfix**: the 10-bit colour now stays on beside DSfix unless DSfix's own SMAA runs on this mod's picture, which happens only when `DSfix.ini`'s `renderWidth` x `renderHeight` is the same size as this mod's resolution, or when this mod's resolution is 1024x720 (DSfix makes that size its render size). SMAA's last pass reads the picture with sRGB decoding, which only an 8-bit picture has: on a 10-bit one the gamma went on twice (tested with DSfix 3.0). DSfix's FXAA and SSAO are fine on the 10-bit picture, and at DSfix 3.0's default size beside this mod's 4K, DSfix's anti-aliasing and SSAO do not run at all.
- **`YieldToDSFix` leaves the HUD and menus to DSfix too**: `UIScaleWorld`, `UIScaleText`, `UIScaleMenus` and `FixBossBarOverlap` now step back with `UIScale`, so the game draws its HUD and menus as it does without this mod. DSfix 3.0's HUD mod and its weapon durability bars (`weaponWearBars`) find the HUD's parts by where the game draws them.

## Phones and Linux (Wine)

- **The controller no longer goes dead when Wine puts its desktop in front.** Under Wine (GameNative, Winlator, Proton) the game's window could lose the foreground to Wine's own desktop window, with nothing on screen to click it back, and the game ignored every button from then on while it ran on (seen on a phone 12 minutes into a session). Under Wine the desktop, or no window, in front now counts as the game's own window. Another program's window in front still counts as leaving; Windows is unaffected.

## Install

Copy the three files next to the game exe. Upgrading from 2.5.0: replace `xinput1_3.dll`; your INI keeps working, and new settings take their defaults when it does not list them. Recommended: exclusive fullscreen with `FullscreenRefreshRate = 0`. Back up your saves. Steam Deck and Linux: launch option `WINEDLLOVERRIDES="xinput1_3=n,b" %command%`.
